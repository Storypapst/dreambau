# ORISO cloud operating rules

These curated nonsecret rules are self-contained. Private Drive/Core, machine Keychain and local skills may be unavailable. Never invent their contents or silently copy stale kit rules. If a private reference is required, report the specific missing reference and stop the dependent work.

1. Before code, read the ticket and project/repository routers. Query the current online graph manifest at https://understand.oriso.org/ua/current/manifest.json and discover service graph URLs there. A403 at /ua/ is not proof the manifest failed. No cached/local graph fallback and no local graph rebuild. Read applicable repository ADRs. For UI work inspect current Storybook contracts/stories before editing components.
2. Keep tool source/cache separate from product source. Resolve the product root at runtime from CLAUDE_PROJECT_DIR or current working directory; the cached Dreambau tooling source is never an ORISO product checkout. Create work branches from dev and PRs against dev. ORISO-E2E uses its established pre-dev integration exception. Neither branch choice changes the runtime target: Dev is https://dev.oriso.org; production is forbidden.
3. Use the Hub through test-access and the session broker for account secrets/OTP. Infisical is the authority behind the Hub; do not fetch arbitrary Infisical secrets or use admin credentials. Runtime Dev and production-test mailbox pool are distinct scopes. Use the fixed synthetic Springfield pool; existing run leases and bounded catalogue sync are allowed within actual identity grants. Reusable pool identities must be preserved; distinguish them from disposable fixtures requiring a real factory/cleanup API. Do not create people, replace accounts or reset passwords to get around missing permissions. Do not print secrets, OTPs, browser state, credentials in argv, screenshots or logs.
4. Run dreambau-cloud-doctor --browser before operating acceptance. API success does not prove Chromium connectivity or product login. Select browser proxy explicitly. Chromium and its contexts must be closed after use; session-state files are credentials. Prefer broker-managed state and existing runtime adapters. Do not claim broker product-login proof without actually testing it.
5. Work one bounded ticket at a time. Use an issue → graph/ADRs → Storybook when applicable → code → focused verification → evidence → reviewable PR flow. Keep current state in issue/PR descriptions, preserve their plain-language opening, and put machine details in labelled fenced text blocks. GitHub text is English. Request repository-approved reviewers when opening a PR. Never approve or merge your own PR, override checks, send Slack/e-mail, deploy without specific human authorization, or activate recurring work before real cloud operating acceptance. The already requested recurring PR discovery/corrections do not need a new generic approval after that gate passes.

Record which gate was measured and where. Public health, scoped Hub metadata, Evidence read permission, browser connectivity, product login, factory provisioning and cleanup are separate facts. Evidence may name actual synthetic actor display names/emails and show product screenshots while withholding every credential/OTP/storage secret. Evidence's unknown-run read probe does not introspect project/environment scopes. Existing APIs do not deliver arbitrary Träger/factory creation or cleanup; those remain separate work. Never report a two-hour autonomous acceptance run or an active schedule until it has actually been performed. Preserve the already authorized recurring scope; do not invent an additional approval gate.
