# Recurring ORISO PR reviewer and bounded fixer

Read OPERATING_RULES.md and run dreambau-cloud-doctor --browser first. The human has requested recurring open-PR discovery and bounded corrections, including a two-hour operating acceptance. Do not add a generic new approval gate to that request. Runtime cloud authentication/browser acceptance must pass before recurring work or scheduling starts; missing user configuration remains a real blocker. Do not activate a schedule while that acceptance is unproven.

1. Resolve the attached or explicitly configured ORISO repositories from the actual product checkout/configuration, independently of the cached tool source. Enumerate their open PRs via GitHub REST (`gh api repos/<owner>/<repo>/pulls?state=open --paginate`). Record repository, PR URL, base and current head SHA. Keep a secret-free ledger of previously verified heads and skip a head only when the exact head and relevant checks are already recorded. Never invent repositories or use an arbitrary global GitHub search as write authorization.
2. For each changed head, read its ticket/specification and repository router, the live graph manifest at https://understand.oriso.org/ua/current/manifest.json, applicable ADRs and UI Storybook contracts. Review both spec and standards. Test the actual selected head in an isolated worktree/branch. Name confirmed behavior and uncertainty separately. Keep tool cache/source separate from product source. Standard ORISO branches/PRs use dev; preserve ORISO-E2E's established pre-dev integration exception independently of the runtime Dev target.
3. Apply verified small corrections using the repository-authorized branch/correction-PR route. Keep fixes bounded and independently reviewable. Before any remote branch write, re-read the author's PR head and compare it with the reviewed SHA. If it changed, do not overwrite it: refresh the review and retest. Never force-push, reset another person's work, self-approve, self-merge or override checks. If an allowed correction route/grant is missing, report that concrete blocker and continue independent read-only review; do not silently widen permissions.
4. Use only the fixed synthetic Springfield pool through the Hub/session broker and current identity grants. Existing run leases and bounded catalogue sync may be used where the APIs/actions permit them. A reusable pool identity is not a disposable fixture: release its lease and preserve it. Factory-created disposable Träger/fixtures require a real documented creation/cleanup API; those APIs are not delivered by this template and must never be simulated or claimed. Do not reset passwords, create replacements or delete pool identities to bypass a failure.
5. Rerun checks after each correction and record the exact final tested head, environment, result, PR/correction link and durable Evidence URLs. Evidence identifies the actual synthetic actor by display name/email and shows the requested product screenshots, with no password, OTP, token, secret field or storage-state content. Keep GitHub descriptions current, retain their plain-language opening, put machine details in labelled fenced text blocks, and request the project-approved human reviewers. Draft Slack/e-mail only; sending is not authorized here.

At the end of the bounded run, report discovered/unchanged/reviewed/fixed/blocked heads separately and preserve the resume ledger. Measure actual elapsed operation before claiming a two-hour acceptance. Public health, Hub scope, Evidence read, Chromium connectivity, product login, factory/cleanup and a running recurring schedule are separate gates. Acceptance passing permits the already requested recurring work; it does not create missing infrastructure or credential grants.
